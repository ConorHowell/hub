Read this first

This is one operator's setup, not a set of requirements.

None of what follows is needed to use Claude Code well. It is a description of habits that accumulated on one machine, across a handful of small static-site projects, run by one person. Some of it exists to work around problems you may never have. Some of it is taste.

The generic guide — the part that is true for anyone — is at the AI hub root. Read that first. Come here only if a concrete worked example is more useful to you than advice, which it often is.

How to read this

Treat every rule below as "this is what I do", never "this is what you must do". Where a rule exists because something actually broke, the cause is stated — the cause is the transferable part, not the rule.

The worktree pre-flight

One command, before spawning any worktree agent. It prevents the entire failure class below.

git rev-list --count origin/main..main

This must print 0. If it prints anything else, do not spawn a worktree agent yet.

Why

A worktree agent branches from origin/main — the last pushed commit — not from your local HEAD. If you have local commits that have not been pushed, the agent's branch does not contain them.

The agent then does honest work on a base that is missing your recent changes. When you diff its branch against your local main, every line you committed-but-did-not-push shows up as a deletion. Merging that branch phantom-reverts your own unpushed work, and it looks like the agent did it.

This is the cause

Every "stale base" symptom further down this page — surprise - lines in git diff --stat, duplicate const declarations, a worktree whose git log tops out before your recent commits — traces back to this one thing. The recovery section exists because the pre-flight was skipped.

The two fixes

  • Push first. Ship the dependency through your normal pipeline, then spawn the agent. This is the right answer almost always.
  • Skip worktree isolation. Run the agent on the main working tree instead. You lose parallel-safety and the ability to throw the branch away, so this is for when the unpushed work genuinely cannot ship yet.

Verify it yourself. An agent asked "what commit are you based on?" will frequently report your current local HEAD, because that is what its instructions and its view of the repo imply. It is not lying; it just has no reason to distrust the premise. Run the count command in your own shell.

Worktree agent choreography

The full sequence I run around a worktree agent, start to merge.

1
Pre-flight
git rev-list --count origin/main..main must be 0. See above. Also: identify every git repo in scope first — a subdirectory can have its own .git, and an agent pointed at the parent will not see it.
2
Write the spec to a file if the task is long
Subagents have no checkpoint or resume — one that dies at a session limit mid-task loses everything in its context. So: write the full task spec to disk, point the agent at the file, and tell it to record progress (files changed, step reached) back to disk as it goes. If it dies, a fresh agent picks up the same spec and loses nothing.
3
Spawn with the rules block
Pasted verbatim into every worktree agent prompt, below.
4
Read the Shipping Status block
Not the prose summary. The block is what decides the next action.
5
Diff before trusting anything
git diff main..<branch> --stat. Unexpected - counts on files the agent was not asked to touch means stale base or out-of-lane edits. Do not merge on a surprise.
6
Syntax-check every modified file
node --check, python -m py_compile, bash -n — whatever the language offers. This is what catches a duplicate declaration that a clean-looking diff hides.
7
Merge deliberately, then prune
git merge --no-commit --no-ff, inspect git diff --cached, then commit. Merges do not happen automatically just because an agent said "done". Finish with git worktree prune.

The rules block

Pasted verbatim into every worktree agent prompt. Short on purpose — a long prompt buries the three rules that actually matter.

RULES: use `git -C <absolute-repo-path>` for every git command — never `cd` between bash calls. The working directory persists and causes silent git errors. Do not commit or push. The main thread ships. When done: list every file you changed. Do not merge your own branch. End your final message with a Shipping Status block.

Background agents auto-deny permission prompts. A backgrounded agent that hits an un-allowlisted network call or write fails silently — it does not ask, it just gets a denial and works around it. Run permission-needing agents in the foreground, or pre-grant the specific tools in the project settings allowlist before launching.

Worktrees always pay a cold cache start. The prompt cache is scoped to a working directory, and a worktree is a different directory. Use worktrees for isolation and parallel edits — not as a token saving, because they are not one.

Failure modes

Four things that have actually gone wrong. A is the parent of D.

ModeSymptomFix
A — stale base git log --oneline -3 in the worktree tops out before your recent commits; git diff main..<branch> --stat shows deletions on files the agent never opened. Rebase onto main before merging. Prevented entirely by the pre-flight.
B — out of lane Files modified outside the assigned scope. Cherry-pick the intended files, reject the rest.
C — uncommitted git diff main..<branch> looks clean, but git diff HEAD inside the worktree shows modifications — the work was never staged. Commit the unstaged work first, then re-diff. Always check both.
D — duplicate declarations Stale base plus a symbol already added on main → two const/function declarations after the merge. Runtime crash, not a merge conflict, so nothing warns you. Syntax-check every modified file before merging. This is the one that reaches production if step 6 is skipped.

Recovery

When the pre-flight was skipped and the diff looks wrong.

git log --oneline -3 # 1. confirm the real base commit git diff HEAD # 2. find uncommitted work — commit it git rebase main # 3. rebase, resolve conflicts node --check <file> # 4. syntax-check every modified file git merge --no-commit --no-ff <branch> # 5. stage the merge without committing git diff --cached # 6. final read — then commit git worktree prune # 7. clean up

Steps 4 and 6 are the ones that get skipped under time pressure, and they are the two that catch mode D.

Self-cleanup, every session

  • git worktree prune — removes worktrees whose directories are gone.
  • Delete temp files created during the session.
  • Never leave uncommitted changes on a worktree branch — commit or discard, not "later".

Session handoff

One file, overwritten at the end of every session, read at the start of the next.

docs/progress.md is the only thing that carries state between sessions. It is overwritten, never appended — a progress log that grows becomes something nobody reads, and it costs tokens on every session start. Four things go in it:

  • Active task — what was mid-flight when the session ended.
  • Files changed — so the next session does not re-derive them from git.
  • Blockers — anything waiting on a decision or an external thing.
  • Next action — one concrete sentence, not a category.

Everything else that would be tempting to put here belongs somewhere durable instead: an architectural change goes in _SYSTEM/CONTEXT.md, a rule goes in CLAUDE.md, a repeatable procedure goes in a skill.

The Stop hook that enforces it

Writing the handoff is a habit, and habits fail at exactly the moment they matter — the end of a long session. A hook is deterministic where a CLAUDE.md line is advisory, so the reminder lives in settings.json:

{ "hooks": { "Stop": [ { "hooks": [ { "type": "command", "command": "f=docs/progress.md; if [ ! -f \"$f\" ] || [ -n \"$(find \"$f\" -mmin +240 2>/dev/null)\" ]; then printf '%s' '{\"hookSpecificOutput\":{\"hookEventName\":\"Stop\",\"additionalContext\":\"docs/progress.md is missing or over 4 hours stale — write the handoff before closing.\"}}'; fi" } ] } ] } }

It fires when the session stops, checks the file exists and was touched recently, and prints a message if not. It does not block anything — a hook that blocks the end of a session is a hook you will disable within a week.

The matching half is a SessionStart hook that reminds you the file exists at all. Both are generic patterns; the guide covers hooks properly.

Shipping Status & deploy ownership

Agents build and report. The main thread ships. No exceptions, because the exception is what causes the double-deploy.

The block

Every agent that touches a repo ends its final message with this, verbatim:

## Shipping Status - Committed: yes | no — <hash or "none"> - Pushed: yes | no - Deployed: yes | no - Deploy script used: yes | no

A prose summary saying "all done!" is not sufficient and is not accepted. The point of a fixed block is that it is four booleans I can read in one second, in the same place every time, with no room for an agent to be optimistic in prose. If a line is no when it should be yes, that is the next action.

Deploy ownership

ActorDoesNever does
Worktree agent Edits files. Reports what changed. Stops. Commits, pushes, or deploys.
Main thread Reviews the diff, runs the pre-ship review, runs the deploy script. Delegates the deploy.

Two reasons, both learned the annoying way. Only the main thread knows the full set of what is shipping, so only it can judge whether the deploy is coherent. And an agent that deploys on its own bypasses the pre-ship review gate entirely — the gate is a step in the deploy script, so skipping the script skips the gate.

The pre-ship gate. My deploy script stages, runs a review pass over the staged diff, and pauses for confirmation if the review flags anything. Claude Code now ships /code-review and /security-review as built-ins that do the same job interactively — if I were starting today I would use those before writing a custom one.

Folder convention

Two directories per project, so CLAUDE.md can stay short.

PathHoldsLoaded
CLAUDE.md Hard rules and pointers to everything else. Kept short. Every session start — costs on every turn.
_SYSTEM/CONTEXT.md Architecture, current state, known gotchas. Updated in place, version bumped. On demand, via @-reference or when asked.
_SYSTEM/BOT_RULES.md Project-specific hard rules for agents working here. On demand.
docs/progress.md Session handoff. Overwritten each session. Read at session start.

The split exists for one reason: CLAUDE.md is re-sent on every message, so anything that is reference material rather than a rule is cheaper living in a file that gets read when it is relevant. The leading underscore on _SYSTEM/ is purely so it sorts to the top of a directory listing.

Honest note — this predates skills being good. A repeatable procedure that lives in _SYSTEM/ today would be better off as a skill, which loads only when invoked. The convention survives mostly because it is already everywhere.

My agent roster

Four definitions in .claude/agents/, unchanged for months. Not a recommended set — a set that happens to cover what I do.

AgentScopeToolsModelEffort
investigator Read-only code location. "Where is X", "what calls Y". Read, Grep, Bash haiku low
reviewer Adversarial diff review with fresh context — knows the code, not the intent. Read, Grep, Bash sonnet medium
security-reviewer Auth, endpoints, input handling, access control. Read, Grep, Bash sonnet high
<project>-specialist Domain questions and scoped builds inside one project. Read, Edit, Write, Bash, Grep sonnet medium

The effort column is the part I would keep if I could keep only one thing. Effort is set in agent frontmatter and overrides the session level while that agent runs, so the main thread stays at high while the searching and the mechanical work happen cheaply at the edges. Lowering the session effort to save money reliably backfires: at low effort the model scopes to the literal ask, produces a shallow first pass, and the rework costs more than the saving.

One rule I will defend: never cheap out on the security reviewer. A missed vulnerability costs orders of magnitude more than the tokens. Everything else on this table is negotiable.

Model aliases (haiku, sonnet, opus) rather than pinned full IDs — an alias tracks the newest model in its tier and cannot silently go stale on me.

When each one gets used

  • Any search touching more than one file → investigator. Never an inline grep sweep; the output floods the main window and it is exactly the kind of volume a subagent exists to absorb.
  • Any diff before it ships → reviewer. Fresh context is the whole value; a reviewer that watched me write the code agrees with me.
  • Anything touching auth or user input → security-reviewer, before the general reviewer, not after.
  • 3+ files, a new feature, or a cross-file refactor → a general-purpose agent in a worktree, with the choreography above.

Honest notes

Things on this page that are preference, or that I have since stopped believing.

The mandatory caveman-at-session-start rule is redundant

My global rules used to open with a line requiring a compressed output mode to be activated before the first response of every session. Two problems with it.

First, it is a preference. Compressed output saves tokens and I like reading it; neither of those makes it a rule anyone else should adopt, and it is presented on this hub as though it were setup rather than taste.

Second, and more usefully: it is already enforced by a plugin hook. The plugin that provides the mode installs a hook that activates it. Prose in CLAUDE.md restating what a hook already does deterministically is pure cost — it is re-sent on every single message to duplicate something that already happened before the first message. That is the general lesson and it is worth more than the specific rule: if a hook does it, delete the sentence.

It is also third-party code. Any plugin's skills and hooks execute inside your session, so installing one is a trust decision, not a convenience decision. Review the source, and remove it with /plugin if you would rather not.

Things I got wrong for a while

  • "Cache TTL is 5 minutes, so never take a break." On a subscription it is an hour, requested automatically. I built a whole batching ritual around a number that did not apply to me.
  • /compact on a schedule. Compaction costs money to generate a summary. Doing it every N messages, or at a fixed context percentage, or before closing a session, spends that repeatedly for nothing. Compact when one long task genuinely overflows — that is the only rule the hub keeps now.
  • "Challenge your own output." Current models verify their own work without being told, and a leftover verification instruction produces over-verification: more tokens, more latency, no better answer.

All three are covered properly, with sources, in the efficiency section of the guide.
