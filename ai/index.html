Introduction

How Claude Code works — permissions, context, skills, subagents, hooks — plus templates you can download and use in any project.

Claude Code is Anthropic's coding agent for Claude. It reads your project files, runs commands, and edits code directly. Three interfaces, all equivalent: a VS Code / JetBrains extension, a terminal CLI, and a desktop app. Skills, CLAUDE.md, hooks, and ~/.claude/ config behave the same on all three.

This guide is written for someone who has just installed it and wants their first week to be safe and cheap. Sections are ordered by what bites first: permissions before skills, context before agents.

Everything here is meant to be true for anyone. The parts that are specific to one person's habits live separately, under One Operator's Workflow, and are labelled as such.

Conventions

Commands written as /name are typed into a Claude Code session. Commands in a $ block are typed into your shell. Anything described as an opinion is marked as one; everything else is checked against the official documentation.

1 · Install Claude Code

Pick whichever interface you already live in. They share the same config directory, so switching later costs nothing.

Open Extensions (⌘⇧X / Ctrl+Shift+X) → search Claude Code by Anthropic → Install.

Claude Code appears as a panel in the sidebar. Open a project folder and start a session from there. A JetBrains plugin is available through the JetBrains marketplace the same way.

The native installer is the recommended path — it needs no Node.js and updates itself in the background.

macOS, Linux, WSL:

curl -fsSL https://claude.ai/install.sh | bash

Windows PowerShell:

irm https://claude.ai/install.ps1 | iex

Package managers also work — brew install --cask claude-code on macOS, winget install Anthropic.ClaudeCode on Windows. Neither auto-updates, so you upgrade them yourself.

Then, from any project directory:

claude

Run /doctor once after installing — it checks the install for common setup problems.

Download the desktop app from claude.ai/code (macOS, Windows, Linux). It wraps the same agent in a native window.

Config, skills, and hooks are shared with the CLI — anything you set up in one is live in the other.

All three read the same ~/.claude/ directory: settings.json, CLAUDE.md, skills/, agents/, and hooks/.

2 · Permission Modes

Permission mode decides what Claude may do without asking. It is the setting that most determines whether your first week goes well.

Press Shift+Tab to cycle modes in the session, or type /plan to jump straight to plan mode. The mode is not a security boundary in itself — it is how much you have decided to trust the agent for this particular task.

ModeWhat it allowsUse it when
default Prompts the first time each tool is used. You are learning what the agent actually does.
plan Reads files and runs read-only commands. Does not edit. Anything non-trivial. Approve the plan, then switch.
acceptEdits Auto-accepts file edits and routine filesystem commands inside the working directory. You have approved a plan and want it built without a prompt per file.
auto Auto-approves tool calls, with background safety checks that the action matches what you asked for. Steady-state work you are supervising.
dontAsk Auto-denies anything not pre-approved by a rule. You want a hard, silent allowlist and no interruptions.
bypassPermissions Skips prompts almost entirely. Throwaway sandboxes only — see the warning below.
About bypassPermissions

In this mode the agent can delete files, rewrite git history, and run network commands without asking you first. Use it only in a container or a disposable checkout you would not mind losing. If you find yourself reaching for it because prompts are annoying, the right fix is an allowlist or /fewer-permission-prompts, not this.

Allowlists — /permissions

/permissions opens the rules UI. Rules also live in settings.json (global at ~/.claude/settings.json, per-project at .claude/settings.json). A rule is Tool(specifier):

{ "permissions": { "allow": [ "Bash(npm run test:*)", "Bash(git status)", "WebFetch(domain:docs.example.com)" ], "deny": [ "Bash(git push --force*)" ], "ask": [ "Bash(rm *)" ] } }

Three lists, in order of strength: deny blocks, ask always prompts, allow runs silently. Scope rules as narrowly as you can — Bash(npm run test:*) rather than Bash.

/fewer-permission-prompts reads back through your own session history, finds the read-only commands you keep approving by hand, and proposes an allowlist for them. It is the cheapest way to stop being interrupted without weakening anything that matters.

Sandboxing

Separately from permission modes, Claude Code can run Bash inside an OS sandbox — filesystem writes restricted to the working directory and a session temp dir, network access filtered to an allowlist. Enable it in settings.json:

{ "sandbox": { "enabled": true } }

It is implemented with Seatbelt on macOS and bubblewrap on Linux and WSL2. Native Windows is not supported. A sandbox and an allowlist solve different problems: the allowlist decides what may be attempted, the sandbox limits how far a mistake can reach. Running both is the sensible default.

Cost note

Changing permission mode mid-session does not invalidate the prompt cache, so switching modes as the task changes is free. Changing model or effort level mid-session is not free — see Efficiency.

3 · CLAUDE.md

A markdown file that is loaded into every session in that project. It is the cheapest way to stop repeating yourself — and the easiest thing to ruin by writing too much.

Where it lives

  • ~/.claude/CLAUDE.md — global. Applies in every project.
  • <project>/CLAUDE.md — project rules. More specific, so it wins over global.
  • <project>/<subdir>/CLAUDE.md — nested. Loads lazily, the first time a file in that directory is read.
  • @path/to/file.md inside any of them — imports another file, so a long reference doc can live outside the always-loaded file.

Run /init to generate a first draft from the codebase. /memory opens the memory files for editing.

Keep it under about 200 lines

This is the rule that people ignore and then wonder why the agent stopped following instructions. A bloated CLAUDE.md does not make Claude more obedient — it causes Claude to ignore your actual instructions, and it bills on every single turn of every session.

The pruning test for each line: would removing this cause Claude to make mistakes? If not, cut it. Things that fail the test almost every time:

  • Descriptions of what the code obviously does — Claude can read the code.
  • "Double-check your work", "verify your answer", "think step by step". Current models self-verify; these instructions cause over-verification and cost tokens for nothing.
  • Long procedures. Move them into a skill, which loads only when invoked.
  • Anything a hook already enforces. A hook is deterministic; prose is advisory. Prose duplicating a hook is pure overhead.

What earns its place

  • Commands that are not guessable — how to run the tests, how to start the dev server.
  • Hard boundaries — what must never be touched, and why. Giving the reason helps Claude generalise to cases you did not anticipate.
  • Structure that is not obvious from the tree — where the real entry point is.
  • Conventions a newcomer would get wrong.
The mid-session trap

Editing CLAUDE.md during a session does not take effect. Claude keeps using the copy loaded at session start. Your edit applies on the next /clear, /compact, or restart. Confirm what is actually loaded with /context — note that /init generates a file, it does not verify one.

There is also AGENTS.md, a cross-tool convention understood by several coding agents. If you work across tools, keep the shared facts there and let CLAUDE.md hold the Claude-specific parts. A starter template is in All Files.

4 · Context Management

The whole conversation is re-sent on every message. Managing what is in the window is most of what "using Claude Code well" means in practice.

See what is going on

CommandTells you
/contextWhat is consuming the context window right now — memory files, tool definitions, MCP servers.
/statusModel, effort, context percentage, running tasks — without interrupting a response.
/usageToken usage and cost, attributed to skills, subagents, plugins and MCP servers.
/costCost of the current session.

Three ways to shed context

  • /rewind — truncates back to an earlier turn. That prefix is already cached and still warm, so it is the cheapest way to abandon a path that went wrong.
  • /clear — costs nothing. Use it between unrelated tasks. /rename the session first if you might want to /resume it.
  • /compact — replaces history with a summary. This one is not free: you pay to generate the summary. Give it a focus: /compact focus on the auth bug fix.
One compaction rule

Compact only when a single long task overflows the window. Not on a message count, not at a percentage, and not before closing a session — a summary generated at the end only pays off if you actually /resume. Between unrelated tasks, /clear is strictly cheaper.

Checkpoints and /rewind

/rewind can restore the conversation, the code, or both. It is genuinely useful — and it has one limitation that catches people out:

Not a git replacement

Checkpoints capture only changes made through Claude's file-editing tools. Changes made by Bash commands (rm, mv, a build script) or by any external process are not captured and will not be restored. Commit before anything risky.

Related

/fork branches the current session; unlike a subagent it inherits the parent's prefix exactly and reads the parent's cache. /recap summarises what has happened so far without discarding anything. /todos shows the current task list.

One behavioural rule worth more than any command: if you have corrected the same misunderstanding more than twice in a session, /clear and start fresh. The contradictory history is now working against you, and you pay for it on every subsequent message.

5 · Skills

A skill is a folder containing a SKILL.md. Its body loads only when the skill is invoked — which is why procedures belong here and not in CLAUDE.md.

Where skill files come from

There is no magic source. A skill exists because one of these put it on disk:

  • You wrote it — see Write Your Own Skill.
  • A plugin shipped it — installing a plugin from a marketplace brings its skills with it. See MCP & Plugins.
  • A script wrote it — this hub's install-skills.sh embeds the skill bodies and writes them into ~/.agents/skills/, then registers them.
  • It is bundled — some skills ship with Claude Code itself. See Built-in Review Skills.

Claude Code loads skills from ~/.claude/skills/ (global) and .claude/skills/ (project). /skills lists what the current session can see.

Register by symlink, never by copy

Wherever you keep the source of truth, link to it rather than copying it in. A copy drifts silently and you end up running last month's version of your own skill.

mkdir -p "$HOME/.claude/skills" ln -sfn "/absolute/path/to/your/skills/<name>" "$HOME/.claude/skills/<name>" ls -l "$HOME/.claude/skills/<name>" # must print '->' and the source path

Two failure modes worth knowing, because both look like success:

  • ln -sfn pointed at a path that does not exist exits 0 and leaves a dangling link. Always run the ls -l check.
  • If ~/.claude/skills/<name> is already a real directory from an older copy-based install, ln -sfn nests the link inside it and exits 0 — the stale copy keeps loading. Delete the directory first.
Put the important lines at the TOP of a SKILL.md

After a compaction, invoked skill bodies are re-injected — but capped at 5,000 tokens per skill and 25,000 total, oldest dropped first. Truncation keeps the start of the file. A skill whose critical rule sits at the bottom of a long file silently loses that rule after the first compaction, and nothing tells you.

This hub's skills

Four skills, plus the third-party caveman plugin, packed into one self-contained installer. Nothing here is required to use Claude Code — they are examples you can read, run, or ignore.

Write Your Own Skill

One required file. The frontmatter is how Claude decides when the skill applies, so it is worth more care than the body.

SKILL.md

--- name: my-skill description: > What this skill does, and when to use it. Include the phrases a user would actually type. Say when to use it, not how eager to be. --- The most important rules go here, in the first few lines — this is what survives truncation after a compaction. Then the detail, the examples, and the output format.

Naming matters more than it looks: the description is what Claude matches intent against. Describe the situation the skill is for. Avoid shouty phrasing like "CRITICAL: YOU MUST use this" — normal wording triggers more accurately, and aggressive wording causes the skill to fire when it should not.

Register and verify

mkdir -p "$HOME/.claude/skills" ln -sfn "$PWD/skills/<name>" "$HOME/.claude/skills/<name>" ls -l "$HOME/.claude/skills/<name>" diff "$PWD/skills/<name>/SKILL.md" "$HOME/.claude/skills/<name>/SKILL.md"

The diff should print nothing. If it prints a difference, you have a copy rather than a link, and it has already drifted. Start a fresh session and check /skills lists the new name.

An optional README.md beside SKILL.md is for humans — what it does, how to trigger it, what the output looks like.

6 · Subagents

A subagent runs a task in its own context window and returns only a summary. The raw output — thousands of lines of logs, test results, search hits — never enters your session.

Skills and subagents are not the same thing

SkillsSubagents (.claude/agents/)
Invoked byYou, with a slash commandClaude delegates automatically, or you name one
Runs inMain context by defaultAn isolated context window
Model controlInherits the session modelPer-agent — route cheap work to a small model
Context impactOutput lands in the main threadOnly the summary comes back

Defining one

A subagent is a markdown file at ~/.claude/agents/<name>.md (global) or <project>/.claude/agents/<name>.md. Claude reads the description to decide when to route work there, so write it as a description of the situation, not of the agent.

--- name: reviewer description: > Adversarial diff reviewer with fresh context — no knowledge of intent, only the code. Use after any builder finishes, before shipping. tools: - Read - Grep - Bash model: sonnet effort: medium --- You are an adversarial code reviewer. You did not write this code and you do not know why it was written. Report only problems that affect correctness or the stated requirements. First line of your response: APPROVE or FLAG. Then: path:line: severity: problem. fix.

Two frontmatter keys do most of the cost work, and templates usually omit the second:

  • model: — use the tier alias (haiku, sonnet, opus) rather than a pinned full ID. An alias tracks the newest model in its tier and cannot silently go stale.
  • effort: — reasoning effort for this agent, independent of your session. Values run low, medium, high, xhigh, max. This is the real lever: your main session can stay at high effort while a search agent runs at low.

tools: narrows what the agent can do — a read-only investigator with only Read, Grep and Bash cannot edit anything by accident. /agents lists and manages the agents a session can see.

Routing by cost

  • Search, grep, read-only location work → smallest model, effort: low.
  • Scoped one- or two-file edits, diff review → mid tier, effort: medium.
  • Security review and anything adversarial → do not cheap out; keep effort high.
  • Architecture, cross-file design, debugging → keep it on the main thread.

The last one is the counter-intuitive part. Lowering the main thread's effort to save money tends to backfire: a shallow first pass produces rework, and rework costs more than the reasoning would have. Push cost to the edges instead.

Delegate for volume, not for trivia

A subagent starts its own conversation with its own system prompt, so it gets no cache hits on its first call, and it uses the short 5-minute cache window even on a subscription. It is a context win, not automatically a token win. A one-line lookup dispatched to a subagent costs more than doing it inline. Delegate when the output is large.

The cache is also effectively scoped to one machine and one working directory, so an agent running in its own git worktree always pays a cold start. Still the right call for isolation — just not a saving.

A ready-made agent definition template and a full multiagent decision guide are in All Files.

7 · Hooks

A hook is a shell command Claude Code runs at a defined moment in the session. Where CLAUDE.md is advisory, a hook is deterministic: it runs whether or not the model felt like it.

This is the single highest-leverage feature most users never touch. Anything you have written into CLAUDE.md as "always do X" is a candidate to become a hook — and once it is a hook, the prose can be deleted, which also shortens the file that bills on every turn.

Shape

Hooks live under a hooks key in ~/.claude/settings.json (global) or .claude/settings.json (project). Each event holds a list of matchers, each matcher a list of commands. /hooks opens a UI for managing them.

{ "hooks": { "PreToolUse": [ { "matcher": "Bash", "hooks": [ { "type": "command", "command": "/absolute/path/to/guard.sh", "timeout": 30 } ] } ] } }

Useful events include SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PreCompact, SubagentStop, Stop, and SessionEnd. A hook communicates back by printing JSON to stdout, or by exit code: 0 succeeds and its stdout is parsed as JSON; 2 is a blocking error and stderr becomes the reason; any other code is a non-blocking error.

The field that matters most is hookSpecificOutput.additionalContext — text injected into Claude's context. systemMessage, by contrast, is shown to you and is not reliable as instruction to the model. If you want the model to act on it, use additionalContext.

Template — SessionStart context injection

Reads a project state file, if one exists, and injects it so every session starts knowing where the last one stopped. Silent when there is nothing to say.

#!/bin/bash # SessionStart hook. Requires jq for safe JSON string encoding. DIR="${CLAUDE_PROJECT_DIR:-$PWD}" OUT="" [ -f "$DIR/docs/progress.md" ] && OUT="$OUT$(cat "$DIR/docs/progress.md") " if [ -n "$OUT" ]; then printf '{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":%s}}' \ "$(printf '%s' "$OUT" | jq -Rs .)" fi exit 0

Template — Stop reminder

Fires when Claude finishes responding. This one nags only if the state file is stale, so it stays quiet during normal work.

FILE="${CLAUDE_PROJECT_DIR:-$PWD}/docs/progress.md" if [ ! -f "$FILE" ]; then printf '{"hookSpecificOutput":{"hookEventName":"Stop","additionalContext":"No progress file exists. Create one with the current task state before ending this session."}}' elif ! find "$FILE" -mmin -240 -type f 2>/dev/null | grep -q .; then printf '{"hookSpecificOutput":{"hookEventName":"Stop","additionalContext":"The progress file has not been updated in 4+ hours. Update it with the current task state."}}' fi

Template — PreToolUse dangerous-command guard

Inspects the command about to run and denies known-destructive patterns. This is the piece a permission allowlist cannot express well, because it pattern-matches the actual command string. Note the exit code: a deny decision is returned on stdout with exit 0, because on exit 2 stdout is discarded entirely and the reason never reaches Claude.

#!/bin/bash INPUT=$(cat) deny() { printf '{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"%s"}}\n' "$1" exit 0 } # Fail CLOSED. `CMD=$(... || exit 0)` looks like it bails out safely, but the exit # runs in the subshell — CMD ends up empty, every check below misses, and the guard # silently allows everything. Test this path; it is the one that matters. if ! CMD=$(printf '%s' "$INPUT" | jq -er '.tool_input.command // ""'); then deny "Could not parse the tool input, so the command could not be checked." fi check() { if printf '%s' "$CMD" | grep -qE "$1" 2>/dev/null; then deny "Blocked dangerous pattern: $2" fi } # Use [[:space:]] rather than \s — BSD grep on macOS does not support \s in -E. check 'rm[[:space:]]+-rf[[:space:]]+/([[:space:]]|$)' 'rm -rf /' check 'rm[[:space:]]+-rf[[:space:]]+~([[:space:]]|$)' 'rm -rf ~' check 'git[[:space:]]+push[[:space:]]+.*(--force|[[:space:]]-f([[:space:]]|$))' 'git push --force' check 'git[[:space:]]+reset[[:space:]]+--hard' 'git reset --hard' check 'git[[:space:]]+clean[[:space:]]+-[a-z]*f[a-z]*d' 'git clean -fd' check 'chmod[[:space:]]+777' 'chmod 777' check 'DROP[[:space:]]+TABLE' 'DROP TABLE' exit 0

Template — PreCompact preserve list

Runs immediately before a compaction and tells the summariser what must survive. A one-liner, no script file needed.

printf '{"hookSpecificOutput":{"hookEventName":"PreCompact","additionalContext":"PRESERVE DURING COMPACTION: (1) the current task and which step it is on, (2) every file changed this session, (3) any uncommitted changes, (4) the next action to take."}}'

Use additionalContext here, not systemMessage — a systemMessage is displayed to you and does not reach the summariser.

Hooks run with your privileges

A hook is arbitrary shell, executed automatically, with whatever access your user has. Use absolute paths, quote your variables, and never interpolate untrusted input into a command string. Hooks that arrive with a plugin are the same risk with less visibility.

Hooks are also a direct token saving: a PostToolUse hook that greps a test run for failures turns tens of thousands of tokens of output into a few hundred before Claude ever sees them.

8 · MCP & Plugins

Two different extension points that are easy to confuse. MCP adds tools from an external server. A plugin adds skills, agents, hooks and commands from a repository.

MCP servers

The Model Context Protocol lets Claude Code talk to an external service — an issue tracker, a database, a browser — through a standard tool interface. /mcp lists connected servers and their auth state.

The practical guidance is unglamorous: prefer a CLI tool over an MCP server when one exists. If gh, aws, or psql already does the job, Claude can just run it, with no tool definitions loaded into the prefix at all. MCP tool definitions are deferred by default so the cost is usually small, but /context will show you exactly what a given server is consuming.

Plugins and marketplaces

/plugin opens a panel with tabs for discovering, installing and removing plugins, and for managing marketplaces. A marketplace is just a source — a GitHub repository, a git URL, a local path, or a JSON manifest:

/plugin marketplace add owner/repo /plugin marketplace list /plugin install <name>@<marketplace> /plugin list
Trust warning — read this before installing anything

A plugin's skills, agents and hooks execute inside your session with your privileges. A plugin hook can run any command a shell can. A plugin skill can rewrite instructions the model then follows. This is not a sandbox and it is not reviewed by Anthropic.

Install only from sources you have actually looked at. Enabling a plugin's own MCP server can also invalidate your prompt cache for that conversation, so it is worth doing deliberately rather than while browsing.

9 · Built-in Review Skills

Claude Code ships with review skills. Try these before writing your own — most of what people build by hand already exists here.

CommandWhat it does
/code-review Reviews your working diff for bugs and correctness problems. This is the general-purpose one — reach for it before shipping anything.
/security-review Security-focused pass over the pending changes on the branch. Use it whenever a change touches auth, input handling, or anything that reaches the network.
/simplify Quality pass over changed code — reuse, dead code, over-abstraction. It deliberately does not hunt for bugs; that is /code-review's job.
/verify Builds and runs the app to confirm a change actually works, rather than reasoning that it should.
/review Reviews a GitHub pull request, as opposed to your local diff.

So when is a custom review skill worth writing?

When it encodes something the built-ins cannot know:

  • A machine-readable verdict. A custom skill can be told to make its first line APPROVE or FLAG, so a deploy script can branch on it. That is what /ship-review is for.
  • Project-specific failure modes. The mistakes your codebase actually makes, which no general reviewer would look for.
  • A narrower brief. A reviewer told to find gaps will report some even when the work is sound. Instructing it to flag only what affects correctness or the stated requirements is the difference between reviews you read and reviews you learn to ignore.

If none of those apply, use the built-in. It is maintained for you.

10 · Efficiency

Prompting advice that is now wrong, how the prompt cache actually works, and where the money really goes. The full write-up is a download; the essentials are here.

↓ Download EFFICIENCY.md

Advice that has gone stale

Old adviceCurrent position
"Add double-check your work"Delete it. Current models verify their own work; the leftover instruction causes over-verification — more tokens, more latency, no benefit.
"Say think step by step and list the steps"Prefer general over prescriptive. "Think thoroughly" usually beats a hand-written plan, because the model's own reasoning often exceeds what you would have prescribed.
"Tell it what not to do"Say what to do instead. Positive examples beat prohibitions.
"Longer instructions are safer"A bloated CLAUDE.md causes Claude to ignore your actual instructions.
"If in doubt, use [tool]"Causes tool overtriggering. Say when to use a tool, not how eager to be.
"Prefill the assistant turn to force a format"No longer supported on current models — it is a hard API error. Use structured outputs.

The cheapest fix available: grep your own CLAUDE.md, skills and agent files for "double-check", "verify your", "make sure to check" and "think step by step", and delete those lines. Fewer input tokens, fewer output tokens, lower latency, same or better quality.

What actually works

  • Give the reason with the rule. Explaining why helps Claude generalise to cases you did not anticipate.
  • Examples beat description. Three to five relevant, diverse examples steer format and tone better than any amount of prose.
  • Long inputs: material at the top, question at the bottom. For very large inputs, putting the question last can improve quality substantially. Most people do this backwards.
  • Put the role in the system prompt, not the user turn. Even one sentence helps.
  • Write specific prompts. "Improve this codebase" triggers broad scanning. "Add input validation to the login function in auth.ts" does not.
  • Give verification targets — a test case, expected output, a screenshot to match. Self-verifiable work catches its own errors instead of costing a correction round-trip.

The prompt cache

The cache matches on the prefix — the start of the request — and the match is exact. A change anywhere in the prefix recomputes everything after it. There is no per-file or per-segment caching. Two things are part of the cache key without appearing anywhere in the prompt text: the model and the effort level.

Invalidates the whole cacheDoes not
Switching model · changing effort level · turning on fast mode · connecting or disconnecting an MCP server whose tools load into the prefix · denying an entire tool by bare name · upgrading Claude Code Invoking skills and commands · spawning a subagent · hooks · editing repo files · editing CLAUDE.md · changing permission mode · /rewind
The one habit that matters most

Choose your model and effort level at the start of a session, then leave them alone. Dropping to a cheaper model or lower effort mid-session to save money is a full cache miss: it recomputes the entire conversation, and usually costs more than it saves.

Cache lifetime depends on how you authenticate: roughly an hour on a Claude subscription, five minutes on an API key or a cloud provider. On a subscription, the widely repeated "batch everything, never take a break" rule does not apply — normal breaks are fine.

Where the money goes

  • /clear between unrelated tasks. Stale context is re-sent on every subsequent message.
  • Right-size the model. A mid-tier model handles most coding; reserve the largest for architecture and multi-step reasoning.
  • Delegate verbose operations — test runs, log processing, doc fetching — to subagents, so the raw output stays in their window.
  • Move procedures out of CLAUDE.md and into skills. CLAUDE.md bills every turn; a skill body bills only when invoked.
  • Use hooks to preprocess output before Claude ever sees it.
  • Use plan mode for complex tasks. It prevents the expensive rework that follows a wrong initial direction. Skip planning when you could describe the diff in one sentence.

The single best health metric is the ratio of cache reads to cache writes — cache reads bill at roughly a tenth of the standard input rate. If cache creation stays high turn after turn, something in your prefix keeps changing.
